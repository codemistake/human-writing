# Постмортем: недоступность публичного API 3 сентября

## Краткое описание

3 сентября с 11:47 до 13:20 публичный API был полностью недоступен для всех клиентов - 93 минуты. Причина - истёк TLS-сертификат на ingress-контроллере, а cert-manager не смог перевыпустить его вовремя из-за собственного сбоя.

## Хронология

В 11:47 Prometheus зафиксировал рост ошибок TLS handshake до 100%. Алерт не пришёл: правила алертинга для этой метрики не было.

В 11:52 в поддержку пошли обращения от клиентов. В 12:05 сотрудник поддержки вручную уведомил дежурного инженера через PagerDuty.

В 12:10 дежурный начал диагностику и в 12:35 выяснил, что сертификат истёк в 11:47. В 12:40 попробовали перевыпустить сертификат вручную через cert-manager - не получилось: под cert-manager с 28 августа висел в CrashLoopBackOff.

В 12:55 cert-manager перезапустили с исправленной конфигурацией. В 13:12 сертификат перевыпустили через Let's Encrypt. В 13:20 API полностью восстановили.

## Причины

Непосредственная причина - истёк срок действия сертификата. Он выпускается автоматически на 90 дней и должен перевыпускаться за 30 дней до истечения.

Корневая причина - cert-manager с 28 августа перезапускался в цикле из-за некорректного обновления CRD при плановом апгрейде кластера. Из-за этого автоматический перевыпуск не работал 7 дней.

Дополнительно повлияло отсутствие алертов: ни на срок истечения сертификата, ни на состояние подов cert-manager.

## Влияние

93 минуты публичный API был недоступен для всех клиентов - по предварительным оценкам, это около 12% дневного объёма запросов. Мобильные приложения, использующие API, показывали ошибку соединения.

## Что было сделано хорошо

Сотрудник поддержки сам эскалировал проблему дежурному инженеру, не дожидаясь автоматического алерта - это сократило время реакции.

## Что необходимо улучшить

Чтобы это не повторилось:

1. Добавить в Prometheus алерт на истечение сертификата менее чем через 14 дней.
2. Добавить алерт на поды в CrashLoopBackOff в namespace cert-manager.
3. Включить проверку состояния cert-manager в чеклист планового апгрейда кластера.
4. Проверить остальные автоматические процессы на отсутствие алертов при сбое.
