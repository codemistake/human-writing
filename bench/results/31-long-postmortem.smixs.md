# Постмортем: недоступность публичного API 3 сентября

## Краткое описание

3 сентября с 11:47 до 13:20 публичный API был полностью недоступен для всех клиентов - 93 минуты простоя. Причиной стал истёкший TLS-сертификат на ingress-контроллере. Cert-manager, который должен был перевыпустить его заранее, к этому моменту не работал.

## Хронология

В 11:47 Prometheus зафиксировал рост ошибок TLS handshake до 100%. Алерт не сработал - правила для этой метрики просто не было.

В 11:52 в поддержку начали поступать обращения от клиентов. В 12:05 сотрудник поддержки вручную уведомил дежурного инженера через PagerDuty.

В 12:10 дежурный начал разбираться. В 12:35 стало понятно, что сертификат истёк в 11:47. В 12:40 попытались вручную перевыпустить его через cert-manager, но не получилось - под cert-manager с 28 августа висел в CrashLoopBackOff.

В 12:55 cert-manager перезапустили с исправленной конфигурацией. В 13:12 сертификат перевыпустили через Let's Encrypt. В 13:20 API полностью восстановили.

## Причины

Непосредственная причина - истёкший сертификат. Он выпускается автоматически на 90 дней и должен перевыпускаться за 30 дней до истечения.

Корневая причина - cert-manager с 28 августа перезапускался по кругу из-за некорректного обновления CRD во время планового апгрейда кластера. Из-за этого автоматический перевыпуск не работал 7 дней.

Отдельно сыграло роль отсутствие алертов - ни на истечение сертификата, ни на состояние подов cert-manager.

## Влияние

93 минуты публичный API был недоступен для всех клиентов. По предварительным оценкам, это затронуло около 12% дневного объёма запросов. Мобильные приложения, которые используют этот API, показывали ошибку соединения.

## Что сработало хорошо

Сотрудник поддержки не стал ждать и сам эскалировал проблему дежурному инженеру - это сократило время реакции.

## Что нужно улучшить

1. Добавить в Prometheus алерт на истечение сертификата менее чем через 14 дней.
2. Добавить алерт на поды в CrashLoopBackOff в namespace cert-manager.
3. Включить проверку состояния cert-manager в чеклист планового апгрейда кластера.
4. Проверить остальные автоматические процессы на такие же слепые зоны - когда сбой не вызывает ни одного алерта.
