# Постмортем: недоступность публичного API 3 сентября

## Краткое описание

3 сентября с 11:47 до 13:20 публичный API был полностью недоступен для всех клиентов. Суммарная длительность инцидента: 93 минуты. Причина: истёк TLS-сертификат на ingress-контроллере, а сбой cert-manager помешал заметить это вовремя.

## Хронология

11:47. Prometheus зафиксировал рост ошибок TLS handshake до 100%. Алерт не сработал: правила для этой метрики не было.

11:52. В поддержку пошли обращения клиентов.

12:05. Сотрудник поддержки вручную поднял дежурного инженера через PagerDuty.

12:10. Инженер начал диагностику.

12:35. Выяснили: сертификат истёк ещё в 11:47.

12:40. Попытались перевыпустить сертификат вручную через cert-manager. Не вышло: под cert-manager с 28 августа сидел в CrashLoopBackOff.

12:55. cert-manager перезапустили с исправленной конфигурацией.

13:12. Сертификат перевыпущен через Let's Encrypt.

13:20. API полностью восстановлен.

## Причины

Непосредственная причина: истёк сертификат. Он выпускается автоматически на 90 дней и должен перевыпускаться за 30 дней до истечения.

Корневая причина: cert-manager с 28 августа перезапускался по кругу из-за некорректного обновления CRD в рамках планового апгрейда кластера. Из-за этого автоматический перевыпуск не работал 7 дней.

Дополнительный фактор: не было алерта ни на срок действия сертификата, ни на состояние подов cert-manager.

## Влияние

93 минуты публичный API был недоступен для всех клиентов. По предварительным оценкам, это около 12% дневного объёма запросов. Мобильные приложения, которые используют этот API, показывали ошибку соединения.

## Что было сделано хорошо

Сотрудник поддержки не стал ждать и сам эскалировал проблему дежурному инженеру. Это сократило время реакции.

## Что необходимо улучшить

Чтобы не наступить на те же грабли:

1. Добавить в Prometheus алерт на истечение сертификата менее чем за 14 дней.
2. Добавить алерт на поды в CrashLoopBackOff в namespace cert-manager.
3. Включить проверку состояния cert-manager в чеклист планового апгрейда кластера.
4. Проверить все автоматические процессы, у которых нет алерта на отказ.
